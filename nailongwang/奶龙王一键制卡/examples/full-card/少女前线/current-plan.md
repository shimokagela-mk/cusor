# 少女前线 - 角色卡项目计划

## 需求分析结果

### 基本信息
- **创作类型**：世界观设定 + 游戏机制复刻
- **主题方向**：少女前线（Girls' Frontline）全游戏复刻
- **规模**：Macro（宏大世界）
- **风格基调**：对外硬核军事，对内轻松日常；该严肃严肃，该日常日常
- **用户角色**：指挥官
- **卡名**：少女前线

### 核心玩法
- **造枪系统**：通过资源投入制造战术人形，451名人形全部可通过造枪获得
- **配队系统**：编队、阵型、效能计算
- **战役系统**：按游戏章节推进，战斗规则、敌方应对
- **资源系统**：人力/弹药/口粮/零件

### 人形获取方式
- **主线人形**：跟随剧情推进自动加入（AR小队、404等）
- **其他人形**：通过造枪系统获得

- 表格 readable 维护约束：`tables/readable/*.md` 的 `## 当前内容` 第一列不得使用行号、序号或纯数字业务字段；如原业务主键是数字，必须与文本列换位或改为纵表结构，避免 shujuku/sqlite 在导入或更新时把第一列误作行号/索引。
- 本轮已调整 `06-出战配置表.md`、`07-敌人配置表.md`、`08-资源表.md`、`11-人形建造表.md` 的列序/结构和 DDL；已重新执行 readable -> `tables/table-template.json` -> 正则/helper release -> `entries/_build/worldbook.json` / `tables/_build/table-template.json` -> `release/少女前线.json` 的完整构建链。
- 地图表写入约束：前端写 `mapElements` 必须通过 `GFLDataBridge.insertRow('mapElements', data, options)`，桥接层会强制 object-form `insertRow({ tableName, data })` 并将中文字段映射到 SQLite 列，避免生成 `INSERT INTO map_elements DEFAULT VALUES`。
- 地图同步器批量写入约束：`frontend/gfl-map-sync.js` 不得逐条触发保存/刷新；清空旧地图和写入新地图必须串行执行，前 N-1 次 CRUD 使用 `skipChatSave/skipNotify` 静默，最后一次写入负责保存/通知。每次 `insertRow/deleteRow` 都必须检查返回值，不能把 `-1/false` 当成功，否则会出现 AI 返回完整 `items` 但地图元素表只落库前几条的半成品地图。
- 建造页写入约束：控制台只在打开子页时读取一次表格快照，后续前端操作必须自己维护页面内 `resources` / `queue` 状态，不能依赖 shujuku 写入后的通知、刷新或重新 `exportTables()`。shujuku v120 SQLite 模式下不能用 `Promise.all` 并发执行多个 CRUD 写入；`frontend/construction.html` 的开始建造流程必须串行扣减资源并插入 `人形建造表`，写库成功后同步更新本地状态再渲染，避免资源表刷新与建造队列插入互相竞态导致 `INSERT INTO tdoll_construction DEFAULT VALUES` 或写后回读旧快照。
- 建造随机约束：`frontend/construction.html` 开始建造不得用 `当前时间 + 配方` 这类稳定 hash 直接决定本次结果，否则全局时间未推进时同配方会反复生成同一建造时间；应在合格池内按点击随机抽取，并在可行时避开上一轮建造时间，保留“合格池内概率众生平等”的规则。
- 建造队列删除约束：shujuku `deleteRow(tableName, rowIndex)` 的 `rowIndex` 是当前表格 `content` 数组下标，不是稳定业务主键；`frontend/construction.html` 在成功删除或新增本地建造队列后必须重排本地 `queue[].rowIndex/id`，否则连续领取多个完成队列时第二条会沿用旧下标导致越界。
- 点击反馈约束：控制台和战斗 UI 中凡是会等待 shujuku CRUD、遭遇同步或跨窗口写回的按钮，点击后必须立即给可见状态，例如按钮文案变为“写入中/重置中”、禁用防重复点击、toast/status 显示正在处理和失败原因；不得只写 `console.error`。
- 控制台新鲜数据约束：外层 `少女前线控制台` helper 不得长期复用同一个 standby iframe 内存状态；每次打开控制台面板都必须重新设置 `iframe.srcdoc`，让待机页重新从 `AutoCardUpdaterAPI.exportTableAsJson()` 读取最新表。编队页以 `出战配置表` / `后勤队列表` 为唯一初始化真源，数据库表为空时显示空编队，不得回退 `localStorage gfl-formation` 旧草稿。待机看板可保留 `gfl-adjutant` 作为选择目标，但应用时必须用最新 `人形仓库表.当前皮肤` 刷新皮肤与 Live2D 映射。
- 出击状态约束：`当前章节表.出击状态` 是地图模式唯一真源，只能由前端出击/撤退/章节完成入口写入；填表 AI、地图生成 AI 和正文更新规则均禁止修改。地图元素表内容不得反推出击状态。
- 地图绘制约束：未出击和撤退必须执行固定基地元素净化，允许人形/主角/友方/NPC 自由绘制；切入战斗必须先清空地图元素表再交给地图 AI；战斗进行中每轮把历史地图元素作为战斗历史交给 AI 全局重绘。
- 战斗地图真源约束：战斗中可交战单位名单以 `出战配置表` 与 `敌人配置表` 为真源，`地图元素表` 只提供坐标、地形、地标和展示状态；控制台 map 必须严格过滤掉不在 `敌人配置表` 中的敌方单位，但允许 `地图元素表` 绘制友方非战斗人员、主角、NPC、支援人员和剧情单位。战斗 UI 只能从地图元素表读取已配置战斗单位的坐标，不能让地图 AI 写入的额外敌人反向生成战斗单位。战斗 UI 开战同步地图元素表时，应补齐配置表里有但地图表没有的战斗单位，并删除地图表里有但 `敌人配置表` 没有的敌方单位；友方非战斗人员、主角、NPC、地标、障碍、出口不受删除影响。
- 战斗结算移除约束：战斗 UI 点击“结束战斗”写回时，生命值为 0 的我方战斗单位必须从 `出战配置表` 移除，生命值为 0 的敌方战斗单位必须从 `敌人配置表` 移除，并同步删除 `地图元素表` 中同名 `友方/敌方/ally/enemy` 战斗单位行；存活单位只更新当前生命和战斗数值。删除配置表行时必须注意 shujuku `deleteRow` 使用当前表格行下标，不能先删除前排再用旧下标更新后排。
- 战后修理约束：`人形仓库表.损伤状态` 是战后修理真源，限定 `正常/大破/损坏`。战斗 UI 点击“结束战斗”时，曾在战斗中或战斗后低于 40% 最大生命的我方人形写入 `大破`，生命归零写入 `损坏`；大破/损坏人形在仓库和详情页使用当前皮肤的大破立绘。控制台新增“修理”入口（打开仓库页），仓库详情的修理按钮按状态扣除人力/弹药/口粮/零件：大破各 100，损坏各 200，成功后写回 `损伤状态=正常`。编队页禁止把大破/损坏人形新编入主战或后勤队伍，但已在本场战斗中的人形被打成大破不影响本场继续结算。
