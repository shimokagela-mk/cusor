# 少女前线装备模块设计

> 状态：完整设计稿。
> 目的：记录装备模块的表结构、制造规则、装备规则、UI 入口和战斗计算接入方案，作为实现依据。
> 范围：装备图鉴、装备实例、装备栏、装备制造、装备成长、装备校准、战斗伤害计算和特殊战斗规则。

## 1. 设计目标

装备模块目标：

- 让装备成为独立资产，而不是写入人形基础属性串。
- 支持装备图鉴、装备仓库、人形装备栏和装备制造队列。
- 支持装备强化、校准、锁定、来源追踪和实例属性差异。
- 支持装备对战斗数值、夜战命中、全队光环、暴击伤害、换弹时间、前置冷却和霰弹功能性产生实际影响。
- 不把装备属性固化回 `tdoll_warehouse.data`。
- 不把装备加成直接写死进 `battle_config`；战斗启动时从装备表实时合成战斗属性，战斗结束只写回当前生命、损伤状态和必要战斗结果。

## 2. 总体架构

装备属性应作为战斗属性的第三层修正：

```text
人形基础属性 + MOD 属性 + 已装备装备修正 + 战斗环境修正 = 战斗实时属性
```

现有关键真源：

- `tdoll_warehouse`：人形基础属性、MOD 属性、获取状态、皮肤、损伤状态。
- `battle_config`：本场战斗出战人形、当前生命和战斗快照数值。
- `enemy_config`：本场敌人、当前生命和战斗快照数值。
- `frontend/battle.html`：战斗单位构建、命中、护甲、暴击和伤害计算。
- `GFLDataBridge`：控制台各页面统一表访问入口。

装备模块新增真源：

- `equipment_catalog`：装备图鉴/模板。
- `equipment_warehouse`：玩家拥有的装备实例。
- `tdoll_equipment`：人形当前装备栏。
- `equipment_construction`：装备制造队列。

当前程序基线：

- `frontend/gfl-data-bridge.js` 当前用 `TABLES`、`COLUMN_LABELS`、`queryRows()`、`rows()`、`executeSqlBatch()`、`executeSqlMutation()`、`updateCell()`、`insertRow()`、`deleteRow()` 访问表；控制台已是 SQL-only，不能设计依赖全库导出的降级流程。
- `resource_status` 扩展为七项资源：`人力 / 弹药 / 口粮 / 零件 / 心智核心 / 强化材料 / 校准券`。普通资源栏只展示前五项，装备页面单独展示和消耗 `强化材料`、`校准券`。
- `frontend/construction.html` 当前强绑定人形制造：队列表是 `tdoll_construction`，候选池来自 `Bridge.warehouseTdolls()`，领取结果写 `tdoll_warehouse.acquired` 或 `resource_status.心智核心`。
- `frontend/warehouse.html` 当前强绑定人形仓库：只展示 `tdoll_warehouse` 已获取人形，并处理皮肤、看板、心智升级、修理；没有装备页、装备槽或装备实例管理。
- `frontend/battle.html` 当前战斗单位由 `unitFromBattleRow()` 和 `makeUnit()` 构建，战斗循环由 `buildTimeline()` 按 `rof` 与 `attackCount` 排序，`attack()` 只处理命中、护甲、暴击、弹链、生命、大破和战斗日志；没有技能冷却、换弹状态机或装备临时状态字段。
- `battle_config` 与 `enemy_config` 当前只保存战斗快照列：生命、伤害、命中、回避、射速、护甲、移动、穿甲、暴击、弹链；装备派生值只能在战斗启动时合成到内存单位，不能回写成基础表值。

## 3. 表设计

### 3.1 装备图鉴表 `equipment_catalog`

用途：定义装备类别、适配枪种、属性范围、制造时间、权重和战斗规则标签。

DDL：

```sql
CREATE TABLE equipment_catalog ( -- 装备图鉴表
  row_id INTEGER PRIMARY KEY, -- 行号
  equipment_id TEXT NOT NULL UNIQUE, -- 装备ID
  equipment_name TEXT NOT NULL, -- 装备名称
  equipment_category TEXT NOT NULL, -- 装备类别
  slot_type TEXT NOT NULL CHECK(slot_type IN ('配件', '弹匣', '人形', '特殊')), -- 槽位类型
  rarity TEXT NOT NULL CHECK(rarity GLOB '[1-5]★'), -- 星级
  allowed_weapon_types TEXT NOT NULL, -- 可装备枪种
  allowed_tdoll_names TEXT NOT NULL DEFAULT '*', -- 特定人形白名单
  stat_min TEXT NOT NULL DEFAULT '', -- 属性生成下限
  stat_max TEXT NOT NULL DEFAULT '', -- 属性生成上限
  max_level INTEGER NOT NULL DEFAULT 10, -- 最高强化等级
  enhance_growth TEXT NOT NULL DEFAULT '', -- 强化成长规则
  calibration_fields TEXT NOT NULL DEFAULT '', -- 可校准属性
  rule_tags TEXT NOT NULL DEFAULT '', -- 规则标签
  recipe_tags TEXT NOT NULL DEFAULT '', -- 制造配方标签
  construction_time TEXT NOT NULL, -- 制造时间
  construction_weight INTEGER NOT NULL DEFAULT 100, -- 制造权重
  dismantle_yield TEXT NOT NULL DEFAULT '', -- 分解产出
  description TEXT NOT NULL DEFAULT '' -- 描述
);
```

字段约定：

- `equipment_category` 使用用户提供的类别名，例如 `光学瞄具`、`全息瞄具`、`穿甲弹`。
- `slot_type` 固定为 `配件 / 弹匣 / 人形 / 特殊`。
- `allowed_weapon_types` 使用英文枪种逗号分隔，例如 `SMG,RF,AR,MG,SG`。
- “除某枪种外均可装备”的规则直接展开写入 `allowed_weapon_types`，不再单独维护禁止枪种字段。
- `allowed_tdoll_names` 默认 `*`；测距仪这类“部分 RF 可装备”用具体人形名白名单。
- `stat_min` 和 `stat_max` 是装备实例属性生成范围；固定属性装备可让上下限相同。
- `max_level` 定义该装备最高强化等级，低星可低于高星。
- `enhance_growth` 定义强化成长，例如 `伤害=每级+1,命中=每级+1` 或 `按基础属性+3%/级`。
- `calibration_fields` 定义允许校准的属性，例如 `伤害,命中,射速`。
- `rule_tags` 用英文逗号分隔，用于战斗计算中特殊逻辑识别。
- `recipe_tags` 用中文逗号分隔，用于制造候选池筛选，例如 `通用低耗,配件倾向`。
- `dismantle_yield` 定义分解产出，例如 `校准券1，强化材料3`。

### 3.2 装备仓库表 `equipment_warehouse`

用途：记录玩家拥有的每一件装备实例。

DDL：

```sql
CREATE TABLE equipment_warehouse ( -- 装备仓库表
  row_id INTEGER PRIMARY KEY, -- 行号
  instance_id TEXT NOT NULL UNIQUE, -- 装备实例ID
  equipment_id TEXT NOT NULL, -- 装备ID
  base_stats TEXT NOT NULL, -- 实例基础属性
  stats TEXT NOT NULL, -- 实例当前属性
  level INTEGER NOT NULL DEFAULT 0, -- 强化等级
  calibration TEXT NOT NULL DEFAULT '', -- 校准记录
  exp INTEGER NOT NULL DEFAULT 0, -- 强化经验
  locked TEXT NOT NULL DEFAULT '否' CHECK(locked IN ('是', '否')), -- 是否锁定
  acquired TEXT NOT NULL DEFAULT '是' CHECK(acquired IN ('是', '否')), -- 是否拥有
  source TEXT NOT NULL DEFAULT '' -- 来源
);
```

字段约定：

- `instance_id` 是唯一实例，不同装备即使同名也必须有不同 ID。
- `equipment_id` 指向 `equipment_catalog`，名称、类别、星级、槽位和适配规则均从图鉴表读取。
- `base_stats` 是制造或掉落时生成的原始属性。
- `stats` 是该实例经过强化和校准后的当前属性，例如 `命中10，伤害6，射速-4`。
- `level`、`calibration`、`locked`、`source` 属于装备实例状态，不回写图鉴表。

### 3.3 人形装备栏表 `tdoll_equipment`

用途：记录每个人形当前装备了哪些装备实例。

DDL：

```sql
CREATE TABLE tdoll_equipment ( -- 人形装备栏表
  row_id INTEGER PRIMARY KEY, -- 行号
  tdoll_name TEXT NOT NULL, -- 人形名称
  slot_type TEXT NOT NULL CHECK(slot_type IN ('配件', '弹匣', '人形', '特殊')), -- 槽位类型
  equipment_instance_id TEXT NOT NULL, -- 装备实例ID
  UNIQUE(tdoll_name, slot_type),
  UNIQUE(equipment_instance_id)
);
```

约束含义：

- 同一人形同一槽位只能装备一件。
- 同一装备实例不能同时装备给多个人形。
- 装备适配规则不只靠 SQL 约束完成，前端写入前必须校验枪种、白名单和槽位。

### 3.4 装备制造队列表 `equipment_construction`

用途：独立记录装备制造队列，不与现有 `tdoll_construction` 混用。

DDL：

```sql
CREATE TABLE equipment_construction ( -- 装备制造表
  row_id INTEGER PRIMARY KEY, -- 行号
  start_time TEXT NOT NULL, -- 开始时间
  construction_time TEXT NOT NULL, -- 制造时间
  cost_manpower INTEGER NOT NULL DEFAULT 0, -- 消耗人力
  cost_ammo INTEGER NOT NULL DEFAULT 0, -- 消耗弹药
  cost_ration INTEGER NOT NULL DEFAULT 0, -- 消耗口粮
  cost_parts INTEGER NOT NULL DEFAULT 0, -- 消耗零件
  recipe_type TEXT NOT NULL DEFAULT '普通装备制造', -- 配方类型
  result_seed TEXT NOT NULL DEFAULT '', -- 结果种子
  result_equipment_id TEXT NOT NULL DEFAULT '', -- 结果装备ID
  candidate_pool_hash TEXT NOT NULL DEFAULT '' -- 候选池哈希
);
```

设计理由：

- 人形制造和装备制造的结果池、公式、时间、领取逻辑不同。
- 分表能避免现有 `construction.html` 的人形建造规则被污染。
- UI 在建造页使用 `人形制造 / 装备制造` 页签区分两套制造流程。
- 当前人形建造队列没有 `result_seed`，领取结果由页面运行时根据成本和 `TDOLLS` 池推导。装备制造表必须保存 `result_seed`，装备领取必须从 `equipment_catalog` 推导结果，不能复用人形制造的 `q.result` 或重复人形返核心逻辑。
- `result_equipment_id` 在开始制造时即写入，领取时按该模板生成实例，避免模板池变化导致结果漂移。
- `candidate_pool_hash` 记录开始制造时参与抽取的模板 ID 列表哈希。领取时如果哈希不一致，仍以 `result_equipment_id` 为准，并在日志提示图鉴池已变化。

## 5. 属性字段与解析规则

现有战斗属性：

- `生命 / hp`
- `伤害 / damage`
- `命中 / accuracy`
- `回避 / evasion`
- `射速 / rof`
- `护甲 / armor`
- `移动 / movement`
- `穿甲 / armorPiercing`
- `暴击 / critRate`
- `弹链 / ammoChain`

装备模块新增战斗扩展属性：

| 中文字段 | 英文字段 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 暴伤 / 暴击伤害 | `critDamage` | 150 | 暴击伤害倍率百分比。 |
| 夜战抵消 | `nightAccuracyOffset` | 0 | 抵消夜战命中惩罚百分比。 |
| 换弹 | `reloadSpeed` | 0 | 折算为现有 `rof` 时间线修正，不新增换弹状态机。 |
| 前置冷却 | `initialCooldown` | 0 | 记录测距仪等装备的冷却修正；当前战斗页没有技能状态机，接入时只用于日志和特殊装备标签，不生成独立冷却轮次。 |
| 全队命中 | `teamAccuracy` | 0 | 队伍光环，信号弹使用。 |

`GFLDataBridge.parseStats()` 需要扩展识别：

```js
{
  '暴伤': 'critDamage',
  '暴击伤害': 'critDamage',
  '夜战抵消': 'nightAccuracyOffset',
  '换弹': 'reloadSpeed',
  '前置冷却': 'initialCooldown',
  '全队命中': 'teamAccuracy'
}
```

## 6. 装备模板

装备模板必须形成可制造、可掉落、可强化、可校准、可分解的完整模板池。模板池直接对应 `equipment_catalog`，不是类别示例。每一行必须能落入图鉴表，并参与制造候选池、权重抽取、实例属性生成和分解返还。

模板字段压缩说明：

- `属性区间` 是文档压缩写法，落表时必须拆成 `stat_min/stat_max` 两列。
- `成长` 对应 `enhance_growth`。
- `校准` 对应 `calibration_fields`。
- `分解` 对应 `dismantle_yield`。
- `标签` 对应 `rule_tags`，无特殊逻辑则填 `-`。

模板落表映射：

| 文档列 | `equipment_catalog` 字段 |
| --- | --- |
| ID | `equipment_id` |
| 模板 | `equipment_name` |
| 类别 | `equipment_category` |
| 星级 | `rarity` |
| 槽位章节 | `slot_type` |
| 适配 | `allowed_weapon_types` 和 `allowed_tdoll_names` |
| 属性区间 | `stat_min` 与 `stat_max` |
| 成长 | `enhance_growth` |
| 校准 | `calibration_fields` |
| 制造时间 | `construction_time` |
| 权重 | `construction_weight` |
| 分解 | `dismantle_yield` |
| 标签 | `rule_tags` |

属性区间落表格式：

- 文档中的 `伤害6-9` 落表为 `stat_min=伤害=6`、`stat_max=伤害=9`。
- 文档中的固定值 `弹链1` 落表为 `stat_min=弹链=1`、`stat_max=弹链=1`。
- 负数区间必须转换为 `字段=-4~-2`，禁止在落表中使用 `射速-4--2` 这种歧义写法。
- 多属性用英文分号分隔，例如 `伤害=6~9;命中=2~5;射速=-4~-2`。
- `parseStatsRange()` 必须只解析 `字段=min~max` 或 `字段=value`，不解析文档短写。

测距仪白名单：

`测距仪` 的 `allowed_weapon_types` 固定为 `RF`，`allowed_tdoll_names` 固定为：

```text
李-恩菲尔德,WA2000,Kar98k,NTW-20,DSR-50,莫辛-纳甘,SVD,春田,PTRD,SV-98
```

制造配方标签映射：

| 类别 | 默认 `recipe_tags` |
| --- | --- |
| 光学瞄具、全息瞄具、红点瞄具、夜战装备、消音器、备用瞄具、喉缩管 | 通用低耗,配件倾向 |
| 穿甲弹、特殊穿甲弹、状态弹、信号弹、高速弹、霰弹 | 通用低耗,弹药倾向 |
| 外骨骼、弹链箱、固定脚架、防弹插板 | 通用低耗,重装倾向 |
| 芯片、测距仪、特殊穿甲弹、5★稀有型号 | 精密倾向 |
| 2★普通模板 | 通用低耗 |

如果同一模板命中多条规则，`recipe_tags` 合并去重。制造筛选只读取 `recipe_tags`，不通过装备名称猜类别。

## 7. 装备制造设计

### 7.1 配方倾向

装备制造使用“配方决定候选池 + 星级权重 + 建造时间 + 属性区间生成”的公式。

| 配方倾向 | 资源特征 | 高概率产出 |
| --- | --- | --- |
| 通用低耗 | 四项 10-50 | 低星瞄具、消音器、外骨骼 |
| 配件倾向 | 零件高，人力/口粮低 | 光学、全息、红点、夜战、消音器 |
| 弹药倾向 | 弹药高 | 穿甲弹、高速弹、状态弹、霰弹 |
| 重装倾向 | 人力/零件高 | 弹链箱、固定脚架、防弹插板 |
| 精密倾向 | 零件极高，弹药中等 | 芯片、测距仪、特殊穿甲弹 |

配方示例：

| 配方 | 人力 | 弹药 | 口粮 | 零件 |
| --- | --- | --- | --- | --- |
| 低耗装备 | 10 | 10 | 10 | 10 |
| 配件公式 | 30 | 10 | 10 | 90 |
| 弹药公式 | 10 | 150 | 10 | 50 |
| 重装公式 | 150 | 150 | 50 | 150 |
| 精密公式 | 50 | 50 | 50 | 250 |

### 7.2 制造时间

制造时间直接读取 `equipment_catalog.construction_time`。模板池中的制造时间已经按星级和稀有型号分层：

| 星级 | 模板池主时间 | 用途 |
| --- | --- | --- |
| 2★ | 00:05:00 | 低耗公式和早期掉落的普通装备。 |
| 3★ | 00:12:00 | 标准制造结果，构成中低投入主池。 |
| 4★ | 00:25:00 | 中高投入结果，承担大部分可长期使用装备。 |
| 5★ | 00:45:00 | 高投入和精密公式结果，包含稀有型号。 |

同星级稀有型号不另开时间层，靠 `construction_weight` 降低出现率。装备制造沿用人形建造的 `TIME_SCALE=10`，避免同一建造页出现两套时间体感。

### 7.3 领取逻辑

装备制造领取流程：

```text
读取 equipment_construction 队列
-> 按 result_equipment_id 读取 equipment_catalog
-> 用 result_seed 生成装备实例属性
-> INSERT equipment_warehouse
-> DELETE equipment_construction 对应队列
```

实例属性生成：

- 读取模板 `stat_min` 与 `stat_max`。
- 对每个属性在范围内生成数值。
- 用 `result_seed + result_equipment_id + 属性名` 做稳定哈希。
- 领取成功后生成唯一 `instance_id`，例如 `EQ-时间戳-随机短码`。

### 7.4 结果池与权重

装备制造结果按以下顺序确定：

1. 根据资源投入判定 `recipe_type`。
2. 读取 `equipment_catalog` 中与 `recipe_type` 匹配的候选装备。
3. 按 `construction_weight` 抽取装备模板。
4. 开始制造时立即写入 `result_equipment_id`、`result_seed`、`candidate_pool_hash` 和模板自身的 `construction_time`。
5. 领取时只按 `result_equipment_id` 取模板，不重新抽取装备种类。
6. 使用 `result_seed`、`result_equipment_id`、属性名生成实例属性。

权重规则：

- 同一配方倾向内，低星装备权重高，高星装备权重低。
- 高投入配方提高高星候选权重，但不移除低星候选。
- `construction_weight` 是模板基础权重，配方倾向只做倍率修正。
- 同一制造队列领取多次不得改变结果；结果必须由 `result_seed` 稳定决定。
- `candidate_pool_hash` 由候选模板 ID 按字典序拼接后哈希生成。领取时哈希不一致不阻止领取，只记录提示；结果仍以队列中 `result_equipment_id` 为准。

### 7.5 资源消耗与队列写入

开始装备制造时执行单事务：

```text
UPDATE resource_status 扣除人力/弹药/口粮/零件
INSERT equipment_construction 写入开始时间、制造时间、资源投入、配方类型、result_seed、result_equipment_id、candidate_pool_hash
```

领取装备时执行单事务：

```text
INSERT equipment_warehouse 写入 instance_id、equipment_id、base_stats、stats、level=0、calibration、source=装备制造
DELETE equipment_construction 对应队列
```

失败处理：

- 资源不足时禁止写队列。
- 全局时间无效时禁止写队列。
- 候选池为空时禁止写队列，并显示配方不合法。
- 领取时若模板缺失，队列保留并提示装备图鉴缺失，不删除队列。

## 8. 装备强化、校准、锁定与分解

### 8.1 强化

强化读取 `equipment_catalog.max_level` 和 `equipment_catalog.enhance_growth`。

强化规则：

- `level` 从 0 开始，最高不超过 `max_level`。
- 强化消耗同类装备、`resource_status.强化材料` 或四项基础资源。强化材料是资源表资源项，不写入装备仓库表。
- 每次强化后重算 `stats = base_stats + enhance_growth(level) + calibration`。
- 负面属性也可随强化变化，但必须按模板规则明确。例如特殊穿甲弹可保持 `射速-4` 不变，也可强化后变为 `射速-3`，不能隐式变化。
- 强化成功后通过 `executeSqlBatch` 同时更新目标装备 `level`、`exp`、`stats`，并删除被消耗的装备实例、扣减 `resource_status.强化材料` 或扣减四项基础资源。

强化经验公式：

```text
星级系数：2★=10，3★=18，4★=30，5★=50
升到下一级所需经验 = 当前目标等级 * 星级系数
强化材料 1 个 = 10 exp
同类装备经验 = 被消耗装备星级系数 * (1 + 被消耗装备 level * 0.15)
非同类装备经验 = floor(被消耗装备星级系数 * 0.5)
四项基础资源兑换：人力/弹药/口粮/零件各 100 = 10 exp
```

强化执行规则：

1. UI 选择材料后计算本次新增经验。
2. `exp + 新增经验` 达到下一等级需求时连续升级，直到经验不足或达到 `max_level`。
3. 达到 `max_level` 后 `exp` 保留为 0，不再继续吃材料；UI 必须禁用强化按钮。
4. 强化没有失败率。
5. 强化不随机，所有属性只按 `enhance_growth` 确定性计算。

成长表达示例：

```text
伤害=每级+1,命中=每级+1
穿甲=每级+5
暴伤=每级+3
护甲=每级+1,回避=每级-0
```

### 8.2 校准

校准读取 `equipment_catalog.calibration_fields`。

校准规则：

- 只有 `calibration_fields` 中列出的属性可校准。
- 校准消耗 `resource_status.校准券` 或四项基础资源。校准券是资源表资源项，不写入装备仓库表。
- 校准只改变 `calibration` 和 `stats`，不改变 `base_stats`。
- 校准结果必须落在 `stat_min/stat_max` 或强化后允许区间内。
- 校准可改善负面属性，例如 `射速-4` 校准为 `射速-3`，但不能越过模板允许上限。

校准消耗公式：

```text
单次校准券消耗 = max(1, 星级 - 2)
2★=1，3★=1，4★=2，5★=3
四项基础资源替代消耗：人力/弹药/口粮/零件各 200 = 1 张校准券
```

校准算法：

1. 每次校准只选择一个字段，不一次重掷全部字段。
2. 正向属性校准步长为 `+1`，负向属性校准步长为 `+1` 但不能越过 0，除非模板区间允许正值。
3. `calibration` 存储偏移值，例如 `命中+2，射速+1`，不是最终值。
4. `stats` 每次由 `base_stats + enhance_growth(level) + calibration` 重算，不做增量叠加。
5. 校准达到字段上限后，该字段按钮禁用。
6. 校准没有随机失败；玩家选择字段后确定性提升一步。

`calibration` 格式示例：

```text
命中+2，伤害+1，射速+1
```

### 8.3 锁定

锁定规则：

- `locked=是` 的装备不能分解。
- `locked=是` 的装备可以装备、卸下、强化和校准。
- 分解 UI 必须过滤或禁用锁定装备。

### 8.4 分解

分解读取 `equipment_catalog.dismantle_yield`。

分解规则：

- 已装备装备不能分解，必须先卸下。
- 锁定装备不能分解。
- 分解执行单事务：删除被分解的装备实例，并增加 `resource_status.强化材料` 与 `resource_status.校准券`。
- 高等级装备分解返还额外素材，返还量按 `level` 增加。

分解产出示例：

```text
1★：强化材料1
2★：强化材料2
3★：强化材料4，校准券1
4★：强化材料8，校准券2
5★：强化材料16，校准券4
```

## 9. 装备校验规则

装备写入 `tdoll_equipment` 前必须校验：

1. 人形必须存在于 `tdoll_warehouse`。
2. 装备实例必须存在于 `equipment_warehouse`。
3. 装备实例未被其他人形占用。
4. 装备槽位必须匹配 `equipment_catalog.slot_type`。
5. 人形枪种必须命中 `allowed_weapon_types`。
6. 若 `allowed_tdoll_names` 不是 `*`，则人形名称必须在白名单中。
7. 同一人形同一槽位已有装备时，必须先卸下或执行替换流程。

错误提示示例：

- `M4A1 不能装备穿甲弹：穿甲弹仅限 RF/MG。`
- `M1911 不能装备光学瞄具：光学瞄具禁止 HG。`
- `该测距仪仅限指定 RF 人形装备。`

## 10. 战斗计算接入

### 10.1 接入点

现有 `frontend/battle.html` 的关键函数：

- `unitFromBattleRow(side, row, i, tables)`：从表行构造战斗单位 fallback 属性。
- `makeUnit(side, name, x, y, fallback)`：创建单位对象。
- `hitChance(attacker, target)`：命中率计算。
- `attack(attacker, tick)`：命中、护甲、暴击和伤害结算。

接入路径：

```text
unitFromBattleRow 读取 tdoll
-> 读取 tdoll_equipment + equipment_warehouse + equipment_catalog
-> 合并装备 stats 到 tdoll stats
-> makeUnit 生成带装备修正的单位
```

### 10.2 装备属性合并

新增函数：

```js
function equipmentRowsForTdoll(tdollName) {
  // 读取 tdoll_equipment，按 equipment_instance_id 关联 equipment_warehouse。
}

function applyEquipmentStats(baseStats, equipmentList) {
  // 累加 damage / accuracy / evasion / rof / armor / movement / armorPiercing / critRate / ammoChain。
  // 合并 critDamage / nightAccuracyOffset / reloadSpeed / initialCooldown / teamAccuracy。
}
```

合并规则：

- 数值属性直接加总。
- `rof` 最低保持 1。
- `movement` 最低保持 0。
- `critRate` 进入暴击判定时仍应限制在 0-95%。
- `critDamage` 默认 150，装备提供的是额外值，例如 `暴伤25` 后为 175。
- `nightAccuracyOffset` 上限 100。

### 10.3 命中与夜战

现有命中公式：

```js
raw = attacker.accuracy / Math.max(1, attacker.accuracy + target.evasion);
```

夜战扩展：

```js
function effectiveAccuracy(attacker) {
  var accuracy = attacker.accuracy;
  if (battleIsNight() && attacker.side === 'ally') {
    var offset = Math.max(0, Math.min(100, attacker.nightAccuracyOffset || 0));
    var penalty = 0.9 * (1 - offset / 100);
    accuracy = accuracy * (1 - penalty);
  }
  return Math.max(1, accuracy);
}
```

解释：

- 无夜战装备：夜战命中只剩 10%。
- `夜战抵消60`：夜战惩罚从 90% 降至 36%，命中剩 64%。
- `夜战抵消100`：无夜战命中惩罚。

`battleIsNight()` 从当前时间与战斗环境标签共同判断：当前时间处于夜间，或地图/遭遇标签包含 `夜战` 时生效。

### 10.4 暴击伤害

现有暴击：

```js
if (crit) damage = Math.round(damage * 1.5);
```

改为：

```js
if (crit) damage = Math.round(damage * (attacker.critDamage || 150) / 100);
```

这样伪装披风和芯片可以直接影响暴击伤害。

### 10.5 穿甲与护甲

现有逻辑：

```js
var effectiveArmor = Math.max(0, target.armor - attacker.armorPiercing);
var baseDamage = Math.max(1, attacker.damage - effectiveArmor);
```

保留该逻辑。穿甲弹和特殊穿甲弹通过提升 `armorPiercing` 自然提高对装甲单位的伤害。

### 10.6 信号弹全队命中

信号弹效果不只加装备者，应在单位构建完成后应用队伍光环：

```js
function applyTeamEquipmentAuras(units) {
  var allyAccuracyBonus = units
    .filter(function(u) { return u.side === 'ally'; })
    .reduce(function(sum, u) { return sum + (u.teamAccuracy || 0); }, 0);
  units.forEach(function(u) {
    if (u.side === 'ally') u.accuracy += allyAccuracyBonus;
  });
}
```

信号弹装备者的 `射速-` 仍然由自身装备 stats 生效。

### 10.7 换弹、前置冷却与霰弹功能

当前 `frontend/battle.html` 没有换弹轮次、技能冷却或状态机，不能在文档中要求 `reloadTurns`、`initialCooldownTurns` 这类不存在的战斗状态。装备接入必须落在现有 `buildTimeline()`、`hitChance()`、`attack()` 能承载的范围内。

可实现接入方式：

- `reloadSpeed` 折算为 MG/SG 的 `rof` 修正，进入 `buildTimeline()` 的排序和攻击间隔。固定脚架的 `换弹15` 不创建换弹轮次，而是按比例提高可行动频率；同时保留 `移动-` 的负面修正。
- `initialCooldown` 不创建技能冷却轮次。测距仪的 `前置冷却-15` 作为装备标签参与日志描述，或折算为 RF 首次攻击的 timeline tick 修正；若要实装首次攻击提前，只改 `buildTimeline()` 生成第一发 tick 的公式，不新增全局技能系统。
- 霰弹功能只接入 `attack()` 内部的命中后效果：额外伤害、命中日志、护甲临时折减、目标坐标位移或对最近邻敌人的一次轻量溅射。效果必须直接修改当前内存单位和战斗日志，不要求新建持久状态表。

折算公式：

```text
effectiveRof = max(1, rof + floor(reloadSpeed / 5))
firstAttackTick = baseTick + min(0, initialCooldown * 10)
```

说明：

- `reloadSpeed=15` 让 `effectiveRof` 增加 3，直接影响现有 `buildTimeline()` 排序。
- `initialCooldown=-15` 让首次攻击 tick 提前 150，不能小于 1。
- 这两项只影响战斗页内存单位，不写回 `battle_config.rate_of_fire`。

霰弹功能标签：

| 标签 | 效果 |
| --- | --- |
| `knockback` | 命中后将目标内存坐标向后推离 20-40 坐标单位，并写入击退日志；不创建跨轮状态。 |
| `suppression` | 命中后在本次 `attack()` 中降低目标反击日志强度；若实装数值，直接降低目标本轮内存 `rof`，不持久写表。 |
| `armor_break` | 命中后在本次战斗内降低目标内存 `armor`，不写回敌人配置表。 |
| `aoe_pellet` | 对主目标周围敌人造成溅射伤害。 |

## 11. 战斗时序与装备状态

战斗单位只新增能被当前 `makeUnit()` 与 `attack()` 消费的内存字段：

```js
{
  critDamage: 150,
  nightAccuracyOffset: 0,
  reloadSpeed: 0,
  initialCooldown: 0,
  teamAccuracy: 0,
  equipmentTags: [],
  equipmentSummary: ''
}
```

当前战斗流程保持现有结构：

1. `defaultUnits()` 从 `battle_config` 和 `enemy_config` 构建单位。
2. `unitFromBattleRow()` 对友方读取 `tdoll_warehouse`，再读取该人形装备关系并合并装备属性。
3. `makeUnit()` 把装备扩展字段写入内存单位。
4. `applyTeamEquipmentAuras(units)` 在单位列表生成后应用信号弹等队伍光环。
5. `buildTimeline()` 使用装备修正后的 `rof` 或 `effectiveRof` 生成攻击顺序。
6. `hitChance()` 使用装备修正后的命中和夜战抵消。
7. `attack()` 使用装备修正后的伤害、穿甲、暴击率、暴伤、弹链和霰弹标签。
8. 战斗日志记录装备影响，例如“穿甲弹削弱护甲”“信号弹校准火控”“夜战装备抵消命中惩罚”。

战斗结束写回：

- 写回 `battle_config/enemy_config` 的当前生命和战斗位置。
- 写回 `tdoll_warehouse.damage_state`。
- 不写回装备加成后的伤害、命中、射速等派生属性。
- 不修改 `equipment_warehouse.stats`；装备没有战斗耐久损耗，强化、校准、分解是唯一会改变装备实例状态的入口。

## 12. UI 设计与操作流程

### 12.1 仓库页

`frontend/warehouse.html` 新增：

- 人形详情中的装备栏：`配件 / 弹匣 / 人形 / 特殊`。
- 装备属性汇总。
- `更换装备`、`卸下装备` 按钮。
- 大破/损坏人形允许换装，但仍禁止编入新队伍。

当前仓库页只有人形列表、详情、皮肤、看板、心智升级和修理。装备栏必须作为现有 `renderDetail()` 的新增区域接入，复用当前 `selectedName`、`refreshData()`、`renderAll()` 和 `executeSqlBatch()` 写回方式，不能假设已有装备页签或现成装备状态。

人形详情操作流：

```text
打开人形详情
-> 读取 tdoll_warehouse 当前人形
-> 读取 tdoll_equipment 当前人形装备关系
-> 关联 equipment_warehouse 与 equipment_catalog
-> 展示四个槽位、装备名称、星级、当前属性、强化等级、校准记录
-> 点击更换装备
-> 过滤同槽位、可装备枪种、白名单、未被其他人形占用的装备
-> 选择装备
-> executeSqlBatch：删除旧槽位关系，插入新 tdoll_equipment 关系
-> 刷新详情属性汇总
```

卸下装备操作流：

```text
点击槽位中的卸下
-> DELETE tdoll_equipment WHERE tdoll_name = 当前人形 AND slot_type = 当前槽位
-> 刷新装备栏与属性汇总
```

### 12.2 装备仓库页

新增 `frontend/equipment.html`，不把所有装备管理塞进人形仓库。

该页面需要显式加载 `gfl-data-bridge.js`，用新增表注册读取装备表；不能复用 `warehouse.html` 的 `TDOLLS`、`statsOf()`、`activeSkin()` 作为装备数据源。

功能：

- 按类别、星级、适配枪种筛选。
- 显示装备实例属性。
- 显示是否已装备、装备给谁。
- 支持锁定、卸下。

装备详情显示：

- 装备名称、类别、星级、槽位。
- 当前属性 `stats`。
- 基础属性 `base_stats`。
- 强化等级 `level/max_level`。
- 校准记录 `calibration`。
- 来源 `source`。
- 当前装备者：从 `tdoll_equipment` 反查。

装备页状态结构：

```js
var EQUIPMENT = [];
var CATALOG = [];
var EQUIP_RELATIONS = [];
var selectedInstanceId = '';
var equipmentFilter = {category:'ALL', rarity:'ALL', weaponType:'ALL', equipped:'ALL', locked:'ALL'};
var equipmentResources = {enhanceMaterial:0, calibrationTicket:0};
var equipmentBusy = '';
```

装备卡片显示字段：

- 装备名称、星级、类别、槽位。
- 当前属性 `stats`。
- 强化等级 `level/max_level`。
- 锁定标记。
- 已装备标记和装备者名称。

装备详情按钮状态：

- `锁定/解锁`：任何未写入中的装备可点。
- `强化`：未满级且材料/资源足够时可点。
- `校准`：存在可校准字段且校准券/资源足够时可点。
- `分解`：未锁定且未装备时可点。
- `装备给人形`：普通装备可点，材料资源不是装备实例，不出现在装备仓库表。

弹窗状态：

- 强化弹窗展示当前经验、升级后等级、消耗的强化材料/资源/装备实例、强化后属性预览。
- 校准弹窗展示可校准字段、当前偏移、到达上限状态、消耗校准券数量、校准后属性预览。
- 分解弹窗展示返还的强化材料和校准券，要求二次确认。
- 装备给人形弹窗展示所有已获取且未大破/损坏限制外的人形，并按适配结果过滤；不可装备的人形显示禁用原因。

装备操作：

- 锁定/解锁：更新 `equipment_warehouse.locked`。
- 强化：选择素材装备、强化材料或四项基础资源，按 `enhance_growth` 重算 `stats`。
- 校准：消耗校准券或四项基础资源，在 `calibration_fields` 内调整属性，更新 `calibration` 与 `stats`。
- 分解：校验未装备且未锁定，按 `dismantle_yield` 和 `level` 返还强化材料/校准券，删除装备实例。
- 装备给人形：跳转或弹出人形选择，执行装备适配校验并写入 `tdoll_equipment`。

写入函数契约：

- `validateEquipmentForTdoll(tdollName, equipmentInstanceId)` 返回上述 `{ok, code, reason}`。
- `equipToTdoll(tdollName, equipmentInstanceId)` 成功返回 `{ok:true, slotType, replacedInstanceId}`，失败返回错误结构。
- `enhanceEquipment(equipmentInstanceId, materials)` 的 `materials` 结构为 `{instances:['EQI-...'], enhanceMaterial: 3, resources:{manpower:0, ammo:0, ration:0, parts:0}}`。
- `calibrateEquipment(equipmentInstanceId, calibrationInput)` 的 `calibrationInput` 结构为 `{field:'critRate', useTickets: true, resources:{manpower:0, ammo:0, ration:0, parts:0}}`。

写入约束：

- 所有涉及多表变更的操作必须使用 `executeSqlBatch`。
- 新增表必须同时补充 `TABLES` 和 `COLUMN_LABELS`，否则 `rows()`、中文列名映射和 SQL 写入列名都会失配。
- 新增页面必须走 SQL-only API；`getTable()` 当前禁止隐式全库读取，装备页面不能设计依赖未传入 tables 的旧式读取。
- 装备、卸装、强化、校准、分解、制造领取都必须在 UI 中显示“写入中/失败原因”。
- 装备关系写入只修改 `tdoll_equipment`，不修改 `tdoll_warehouse`。
- 强化和校准只修改 `equipment_warehouse`，不修改 `equipment_catalog`。
- 制造领取只新增 `equipment_warehouse` 并删除 `equipment_construction`，不修改图鉴。
- 强化材料和校准券作为 `resource_status` 资源项维护；普通资源栏隐藏这两项，装备页面单独展示和消耗。

## 14. 实施顺序

按以下顺序实施，降低风险：

1. 新增表模板：`equipment_catalog`、`equipment_warehouse`、`tdoll_equipment`、`equipment_construction`。
2. 更新 `GFLDataBridge`：注册装备表、字段标签、读取函数和装备适配校验函数。
3. 战斗页接入装备属性合并、夜战、全队光环、暴击伤害、`reloadSpeed` 折算、`initialCooldown` 首发 tick 修正和霰弹功能性。
4. 构造覆盖全部类别的测试数据，验证命中、暴击、护甲伤害、`rof` 时间线修正、首发 tick 修正、SG 功能弹和装备适配限制。
5. 仓库页显示装备栏和属性汇总。
6. 建造页增加装备制造队列和领取逻辑。
7. 新增装备仓库管理页。
8. 运行 shujuku fake 本地测试与前端预览测试。
9. 构建 release 脚本和角色卡 JSON。

## 15. 验证口径

必须覆盖以下测试：

- 表结构测试：四张装备表能被 shujuku 导入，DDL 注释与中文列名可被 NameMapper 识别。
- 制造测试：资源扣减、队列写入、到点领取、实例属性生成、队列删除在单事务中完成。
- 装备测试：同一人形同槽位不能重复装备，同一装备不能装备给多人，测距仪白名单生效。
- 强化测试：强化等级、经验、当前属性、四项基础资源或强化材料消耗同步更新。
- 校准测试：只能校准允许字段，校准后属性不越界。
- 分解测试：锁定装备和已装备装备不能分解，未锁定未装备装备能返还强化材料/校准券并删除装备实例。
- 战斗测试：装备属性实时合成，光学瞄具影响暴击，穿甲弹影响装甲伤害，夜战装备抵消夜战命中惩罚，信号弹影响全队命中。
- 战斗时序测试：MG/SG 的 `reloadSpeed` 折算影响 `buildTimeline()` 排序，测距仪 `initialCooldown` 影响首发 tick 或日志，霰弹击退/压制/破甲/溅射标签在 `attack()` 中生效。
- 写回测试：战斗结束不把装备加成固化进 `battle_config` 或 `tdoll_warehouse.data`。
- 前端测试：仓库页、装备仓库页、建造页都能读取 SQL-only 表数据并完成写入反馈。

## 16. 定稿约束

- 装备独立成表，不污染人形基础数据。
- 制造独立成表，不混用人形建造队列。
- 战斗实时合并装备属性，不永久写回人形或出战配置。
- 装备制造沿用人形建造的 `TIME_SCALE=10`。
- 装备星级使用 `1★-5★`，低星装备可作为分解、强化和前期掉落基础。
- 测距仪白名单写入 `allowed_tdoll_names`，不在代码中硬编码。
- 夜战判定同时支持当前时间与战斗环境标签。
- 霰弹功能性进入战斗规则，不只作为伤害数值。
- 装备仓库管理页必须提供分解、强化材料返还、强化材料消耗、校准券消耗、锁定保护和已装备保护。
- 大破/损坏人形允许换装，但仍禁止编入新队伍。
- 装备属性不写入 `battle_config` 快照，每次战斗启动从装备表实时计算。
