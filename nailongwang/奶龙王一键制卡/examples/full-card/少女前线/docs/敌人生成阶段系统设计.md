# 少女前线敌人生成阶段系统设计

## 背景

本设计用于补齐章节出击后的敌人生成、敌人资料、现有战斗界面承接、战斗前站位调整、战斗结算与表格回填链路。项目已经存在 `frontend/battle.html` 与 `release/少女前线-战斗界面.regex.json`，它们是当前战斗 UI 的源码与正则注入产物，不应另起一套战斗 UI 正则替代它。新系统应复用现有战斗界面读取 `出战配置表`、`敌人配置表` 并执行站位调整和战斗演算的能力，只扩展同楼遭遇标签解析、敌人资料读取、敌人配置生成和结算回填。现有 `敌人配置表` 是运行态表，只记录当前战斗中已经进入战场的敌方单位，最多 5 行。新系统需要增加静态 `敌人资料表`，并由章节世界书和系统层战斗规则共同约束本楼剧情可遇到哪些敌人、何时允许遭遇 Boss、以及前端如何把候选敌人实例化为具体战斗数值。

## 核心原则

- 章节世界书负责描述本章节可能遇到的敌人、精英单位和剧情 Boss。
- 系统层战斗世界书负责约束正文叙事不能乱刷敌人、不能超过当前战斗容量、不能提前刷 Boss，并要求正文在发生战斗遭遇时输出战斗界面可解析的同楼遭遇标签。
- `敌人资料表` 是静态资料源，保存敌人基础属性档位、阵营、类型、标签、技能摘要和剧情定位。
- `敌人配置表` 是运行态出战表，只保存当前战斗已生成敌人的具体数值和当前生命。
- 正文写自然遭遇叙事；发生战斗遭遇时，正文末尾必须输出现有战斗界面可抓取的同楼遭遇标签块。
- 如果判定需要新增敌人，前端根据 `敌人资料表` 与动态数值规则生成具体数值并写入 `敌人配置表`。
- `敌人配置表` 最多 5 行，任何规则、正则、前端写表都不得突破 5 个敌人。
- Boss 必须和当前章节剧情对齐；如果现有敌方资料没有对应 Boss，则维护者应补入 `敌人资料表`，不能用势力名、抽象概念或不相关 Boss 顶替。

## 表格分工

### 现有战斗界面正则

已有文件：

```text
frontend/battle.html
release/少女前线-战斗界面.regex.json
```

定位：

- `frontend/battle.html` 是当前战斗界面源码，已经读取 `出战配置表`、`敌人配置表`，支持站位调整、战斗演算和战斗扩写提示词发送。
- `release/少女前线-战斗界面.regex.json` 是当前战斗界面的正则注入产物，负责匹配本楼遭遇标签并注入独立战斗模拟 UI。
- 敌人生成阶段不重新设计或替换该战斗界面正则。
- 后续落地时，应在 `frontend/battle.html` 对应逻辑中扩展同楼遭遇标签解析、`敌人资料表` 查询、`敌人配置表` 生成、5 敌人上限校验、站位准备和战斗结算回填。
- `release/少女前线-战斗界面.regex.json` 不应继续使用 `/$/g` 作为正式触发条件；正式方案应把 `findRegex` 改为匹配 `<gfl-battle-encounter>...</gfl-battle-encounter>`，命中遭遇标签时才注入战斗 UI。
- 正则替换时必须把匹配到的遭遇标签内容作为隐藏数据交给战斗 UI 脚本，例如写入隐藏 `<script type="application/json" class="gfl-encounter-source">...</script>` 或隐藏 `<textarea class="gfl-encounter-source">...</textarea>`；战斗 UI 启动后直接读取该隐藏节点，不再从整楼 DOM 里到处查找。
- release 文件是构建产物时，优先维护对应源码或构建输入；只有明确需要临时热修 release 产物时才直接改 release JSON。

### 敌人资料表

建议新增表：

```text
敌人名称 | 阵营 | 敌人类型 | 威胁等级 | 基础档位 | Boss标记 | 章节绑定 | 标签 | 属性模板 | 技能摘要 | 剧情定位 | 数据来源
```

字段含义：

- `敌人名称`：敌方单位标准中文名，必须用于正则捕获、敌人配置表和章节 Boss 判定。
- `阵营`：如 `铁血工造`、`正规军`、`帕拉蒂斯`、`其他势力`、`自定义`。
- `敌人类型`：如 `普通`、`精英`、`Boss`、`召唤物`、`剧情特殊`。
- `威胁等级`：用于剧情和动态数值生成，建议 `低`、`中`、`高`、`极高`、`章节Boss`。
- `基础档位`：保存原始数据中的 `A`、`B`、`C`、`D` 等档位，允许组合写法如 `生命A,伤害B,命中C`。
- `Boss标记`：`是` 或 `否`，用于筛选章节 Boss 候选。
- `章节绑定`：允许为空；若只应在特定章节出现，填写章节名列表。
- `标签`：如 `近战`、`远程`、`装甲`、`高闪避`、`高命中`、`机械`、`涅托`、`铁血头目`。
- `属性模板`：若已经有具体数值，可写完整属性；若只有档位，写档位模板。
- `技能摘要`：简述前端或 AI 需要知道的机制，不写复杂公式。
- `剧情定位`：说明该敌人在剧情中的用途，例如 `塌缩点终局对手`、`镜像论关键敌方单位`。
- `数据来源`：如 `gf_enemy_data`、`网页补全`、`维护者设计`。

`敌人资料表` 不记录当前生命，不参与战斗消耗。它只回答“这个敌人是什么、能在哪里出现、基础能力档位是什么”。

### 敌人配置表

现有 `敌人配置表` 保持运行态职责：

```text
敌人名称 | 出战位 | 当前生命 | 最大生命 | 伤害 | 命中 | 回避 | 射速 | 护甲 | 移动 | 穿甲 | 暴击 | 弹链
```

约束：

- 当前内容默认为空。
- 只由前端写入、更新、删除。
- 新增敌方出战位时总行数不得超过 5。
- `当前生命` 初始化时等于 `最大生命`，或在剧情特殊生成时不超过 `最大生命`。
- `敌人名称` 必须能在 `敌人资料表` 找到；临时剧情 Boss 必须先进入 `敌人资料表` 再生成。

### 总章节表

`总章节表.章节Boss` 应指向 `敌人资料表.敌人名称`。章节胜利结算仍按当前设计读取 `敌人配置表`：当当前章节 Boss 在 `敌人配置表` 中 `当前生命 <= 0` 时，判定章节胜利。

如果某章 Boss 暂无资料：

- 不在 `章节Boss` 中填阵营名、剧情人物名或抽象目标。
- 先在 `敌人资料表` 新增一个与剧情对齐的 Boss 条目。
- 缺少官方数值时，`数据来源=维护者设计`，并按 Boss 动态数值规则生成。

## 章节世界书职责

每个章节世界书应增加或整理以下信息：

```text
本章节可能敌人：<敌人名称列表>
本章节精英敌人：<敌人名称列表>
本章节Boss：<敌人名称或无>
敌人出现节奏：<前期/中期/后期/终局>
禁止出现：<不应在本章出现的敌人或阵营>
```

章节世界书只给候选范围和剧情语境，不直接写 `敌人配置表`。正文 AI 在生成遭遇时，必须从当前章节世界书允许的敌人池中选择。

对于 `终章`：

- `本章节Boss` 默认为 `无`。
- 允许根据玩家与 AI 共同推进的新主线逐步引入新敌人。
- 一旦出现长期主线 Boss，必须先补入 `敌人资料表`，再允许成为章节 Boss 或新增敌人。

## 系统层战斗世界书

建议新增一个系统层世界书条目，作用是规范正文 AI 对战斗遭遇的叙事边界和同楼遭遇标签格式。它不属于某个章节，而是全局控制敌人出现逻辑、敌人数量上限、Boss 出场条件，以及战斗界面如何从当前楼正文中读取“当前敌人/新增敌人”。

系统层规则：

- 每场战斗最多允许 5 个可攻击敌人。
- 总敌人数 = 当前敌人数 + 新增敌人数。
- 如果当前已有 5 个敌人，禁止新增敌人。
- 正文可自然描写当前敌人继续追击、增援抵达或 Boss 介入；若本楼触发战斗，必须在正文末尾输出同楼遭遇标签块。
- 当前敌人以 `敌人配置表` 已存在行作为准。
- 新增敌人必须来自当前章节世界书允许的敌人池，且必须存在于 `敌人资料表`。
- Boss 只能在剧情到达对应阶段时出现，不能因为战斗空缺而提前刷出。
- 如果正文只是行军、侦察、对话、撤离或整备，不输出遭遇标签块。

推荐同楼遭遇标签格式：

```text
<gfl-battle-encounter>
当前敌人: 出战位=1;敌人名称=稻草人;状态=继续战斗
新增敌人: 敌人名称=巡游者;数量=1;威胁等级=低;出场原因=前方巡逻单位接敌
新增敌人: 敌人名称=稻草人;数量=1;威胁等级=章节Boss;出场原因=本章Boss正式介入
敌人总数: 2
</gfl-battle-encounter>
```

战斗界面正则应直接匹配该标签，建议匹配策略：

```text
findRegex: /<gfl-battle-encounter>[\s\S]*?<\/gfl-battle-encounter>/g
```

替换策略：

```text
replaceString = 原始遭遇标签 + 隐藏遭遇数据节点 + 战斗 UI HTML
```

必须保留原始标签或等价隐藏数据，避免战斗 UI 启动后拿不到当前敌人与新增敌人。

格式要求：

- 标签名固定为 `gfl-battle-encounter`，必须成对出现。
- `当前敌人` 行只能引用 `敌人配置表` 已存在的出战位和敌人名称。
- `新增敌人` 行只能写敌人名称、数量、威胁等级和出场原因，不写生命、伤害、命中等具体数值。
- `敌人总数` 必须等于当前敌人数量加新增敌人数量，并且不得超过 5。
- 无战斗遭遇时不输出该标签。

具体生命和战斗数值由前端根据 `敌人资料表` 生成，不由正文 AI 填具体数值。

## 现有战斗界面承接与前端写表

现有战斗界面被遭遇标签正则命中并注入后执行以下流程：

1. 读取 `敌人配置表` 当前行数。
2. 从正则替换保留下来的隐藏遭遇数据节点读取 `<gfl-battle-encounter>...</gfl-battle-encounter>` 内容。
3. 解析 `当前敌人`、`新增敌人` 和 `敌人总数`。
4. 读取当前章节、当前章节世界书允许的敌人池和 `敌人资料表`。
5. 校验 `敌人总数 <= 5`。
6. 校验 `当前敌人` 均已存在于 `敌人配置表`。
7. 校验新增后 `敌人配置表` 总行数不超过 5。
8. 校验新增敌人均存在于 `敌人资料表`，且允许在当前章节出现。
9. 为每个新增敌人分配空闲 `出战位`。
10. 根据 `敌人资料表` 和动态数值规则生成具体属性。
11. 写入 `敌人配置表`。
12. 打开或刷新战斗界面。

失败处理：

- 敌人总数超过 5：拒绝写入，战斗 UI 提示“敌方单位超过上限”。
- 新增敌人不在资料表：拒绝写入，提示维护者补充敌人资料。
- 新增 Boss 与当前章节不匹配：拒绝写入，提示“Boss 与当前章节不一致”。
- 当前楼不存在遭遇标签：战斗界面正则不应触发，不注入战斗 UI。

## 动态数值生成规则

原始敌方数据存在 `A`、`B`、`C`、`D` 档位，因此前端需要把档位转成具体数值。建议采用“章节进度 + 威胁等级 + 敌人类型 + 随机扰动”的确定性生成规则。

### 基础档位区间

建议第一版区间：

```text
生命: D=120-220, C=221-420, B=421-760, A=761-1200, S=1201-1800
伤害: D=12-22, C=23-38, B=39-58, A=59-85, S=86-120
命中: D=10-20, C=21-38, B=39-58, A=59-80, S=81-105
回避: D=4-12, C=13-28, B=29-50, A=51-78, S=79-110
射速: D=20-35, C=36-55, B=56-75, A=76-95, S=96-120
护甲: D=0-5, C=6-18, B=19-38, A=39-65, S=66-95
移动: D=4-6, C=7-9, B=10-12, A=13-15, S=16-18
穿甲: D=0-15, C=16-35, B=36-65, A=66-95, S=96-130
暴击: D=0-5, C=6-15, B=16-30, A=31-45, S=46-60
弹链: D=0, C=0-1, B=1-2, A=2-4, S=4-6
```

### 修正倍率

按敌人类型修正：

```text
普通: 1.00
精英: 1.25
Boss: 1.75
章节Boss: 2.20
召唤物: 0.70
剧情特殊: 由属性模板指定
```

按章节推进修正：

```text
早期章节: 0.85
中期章节: 1.00
后期章节: 1.20
终局章节: 1.35
终章: 依据当前主线强度取 1.20-1.50
```

按威胁等级修正：

```text
低: 0.80
中: 1.00
高: 1.20
极高: 1.45
章节Boss: 1.75
```

最终数值公式：

```text
基础值 = 档位区间内的确定性取值
最终值 = round(基础值 * 敌人类型倍率 * 章节推进倍率 * 威胁等级倍率)
```

确定性取值应使用 `章节名 + 敌人名称 + 出战位 + 当前楼层标识` 作为 seed，避免同一次捕获在刷新后生成不同数值。

### 属性模板优先级

数值来源优先级：

1. `敌人资料表.属性模板` 中已有具体数值。
2. `敌人资料表.基础档位` + 动态数值规则。
3. Boss 缺资料时的维护者设计模板。

不得由正文 AI 在遭遇标签中直接给具体数值覆盖前端生成结果。

## Boss 补全规则

如果当前剧情 Boss 不在敌人资料里有数据，应按以下顺序处理：

1. 查官方或百科敌方名，确认该 Boss 的标准名称。
2. 若 `gf_enemy_data` 有资料，导入到 `敌人资料表`。
3. 若 `gf_enemy_data` 没有资料但网页能确认剧情 Boss，新增 `数据来源=网页补全` 的资料行。
4. 若官方无战斗数值，维护者按剧情强度设计 `属性模板` 和 `技能摘要`，并标记 `数据来源=维护者设计`。
5. 更新章节世界书的 `本章节Boss` 和 `总章节表.章节Boss`，两处名称必须一致。

Boss 设计要求：

- 名称必须和剧情对齐。
- 阵营和标签必须符合章节语境。
- 不得把 `帕拉蒂斯`、`威廉`、`主脑` 这类势力、人物或抽象目标直接当作敌人名称，除非它们已经被设计成可战斗单位并进入 `敌人资料表`。
- Boss 的 `技能摘要` 应体现剧情特点，但第一版不要求实现复杂技能，只需供战斗 UI 或后续规则扩展读取。

## 战斗 UI 流程

完整流程：

1. 正文 AI 根据当前章节世界书写出遭遇剧情。
2. 系统层战斗世界书约束正文只能自然描写当前章节允许的敌人；若触发战斗，在正文末尾输出 `<gfl-battle-encounter>` 标签。
3. 现有战斗界面正则直接匹配 `<gfl-battle-encounter>...</gfl-battle-encounter>`，命中后注入战斗 UI。
4. 正则替换保留遭遇标签或写入隐藏遭遇数据节点，战斗 UI 脚本从隐藏数据节点读取并解析遭遇内容。
5. 前端校验当前敌人、新增敌人、敌人总数和章节 Boss 合法性。
6. 前端把合法新增敌人实例化为具体数值并写入 `敌人配置表`。
7. 前端打开战斗界面，进入战斗准备状态。
8. 用户在战斗开始前调整己方站位。
9. 用户确认后开始战斗。
10. 战斗 UI 根据 `出战配置表` 和 `敌人配置表` 执行战斗。
11. 战斗结束后回填 `出战配置表`、`敌人配置表`、资源消耗、战利品、地图状态和章节胜利状态。
12. 若当前章节 Boss 被击败，章节胜利结算流程更新 `总章节表` 与 `当前章节表.当前阶段`。

## 站位调整

战斗开始前必须允许调整站位：

- 己方读取 `出战配置表.出战位`。
- 敌方读取 `敌人配置表.出战位`。
- 调整阶段只改变站位，不结算伤害。
- 用户确认后锁定站位并开始战斗。
- 战斗中若允许位移，应由战斗规则写回站位或地图状态，不直接修改章节状态。

## 结算回填

战斗结算后需要回填：

- `出战配置表`：更新人形当前生命、状态、必要时更新出战位。
- `敌人配置表`：更新敌人当前生命；死亡敌人保留到本轮结算完成，便于 Boss 胜利检测。
- `资源表`：扣除弹药、口粮、修复或其他战斗消耗。
- `地图元素表`：下一轮地图绘制时根据最新出战和敌人状态刷新。
- `总章节表`：仅当章节 Boss 被击败时更新当前章节为 `已完成`。
- `当前章节表`：仅胜利结算更新 `当前阶段=已完成`，不修改 `出击状态`。

死亡敌人的清理建议放在结算后的下一次遭遇生成或撤退流程中处理，避免 Boss 死亡瞬间被删除导致胜利检测失败。

## 敌人数上限

上限规则必须在三层同时执行：

- 系统层世界书：要求 AI 输出 `敌人总数 <= 5`。
- 战斗界面正则层：只有出现 `<gfl-battle-encounter>` 时才注入战斗 UI。
- 战斗界面解析层：解析遭遇标签后若超过 5，拒绝写表。
- 前端写表层：插入前再次读取 `敌人配置表` 行数，保证插入后不超过 5。

如果正文叙述出现更多敌军，应写成背景压力或远处部队，不进入 `敌人配置表`，也不显示为可攻击目标。
